# Preregistration — R-P1.69: a bigger held-out set and a without-replacement sampler

Claim `346c9f13-5bce-4a63-b6ad-c9844a0f57a2`, registered at **prior 0.5** before the run. Freeze on origin before
any measurement. Status at freeze: **not measured**.

R-P1.68 failed its faithfulness prediction and named exactly what the next
attempt needs:

> "The next attempt needs a **larger held-out set** (so the noise floor drops
> below the bias) and a **without-replacement or weighted** sampler, or an exact
> posterior that does not enumerate."

This card supplies the first two and re-asks the same question: can a sampled
support stand in for exhaustive enumeration, so the pools an operator actually
has (63 and 117 candidates) become measurable?

## What was actually wrong, restated so the fix targets it

At `n = 4`, `M = 2000`, sampled precision was **0.444** against exhaustive
**0.333** — a bias of +0.111, consistently upward, on 12 held-out cases carrying
36 proposal slots. Two candidate causes, and R-P1.68 could not separate them:

- **A — duplicate weighting.** Sampling *with replacement* draws some worlds
  twice, and a top-3 argmax over that support moves toward the duplicated
  worlds. Measured: 1989 distinct of 2000 draws at `n = 8`, so duplicates exist.
- **B — sample noise.** 12 cases cannot resolve a 0.111 gap when the fixture's
  own draw-to-draw sd is 0.038 and its range is 0.083–0.250.

## Design — three changes, each traceable to one of those causes

1. **Without replacement.** Draw the support as a uniform sample of *distinct*
   completions (reservoir-free: shuffle indices and take `M`), so no world is
   weighted twice. This targets A directly.
2. **A larger held-out set.** `HELDOUT = 120` cases instead of 12, from seeds
   disjoint from `DEV`. 360 proposal slots instead of 36, so the standard error
   of a precision estimate falls by ~√10. This targets B.
3. **The same decoder, sensor, `k` and metric.** Nothing else changes.

Cells: `n ∈ {3, 4}` where both arms are computable (the faithfulness test), plus
`n ∈ {6, 8}` sampled-only (the point of the exercise). `M ∈ {2000, 8000}`,
`k ∈ {8}` as the primary cell and `k ∈ {4, 12}` as secondary. Exhaustive arms at
`n = 3, 4` are computed by the same code path, and the 120-case exhaustive run is
the ground truth.

**Cost measured before freeze** (so the grid is computable, not hoped for): a
`n = 8`, `M = 2000` case takes ~0.6 s of decode plus queries; 120 cases × 4 `n` ×
2 `M` × 3 `k` is roughly 1–2 h. If a cell overruns, it is reported as not run
rather than silently dropped.

## Frozen predictions

- **P1 — without replacement removes the bias.** At `n = 4`, `k = 8`, `M = 8000`,
  sampled precision is within **±0.05** of exhaustive **and** the bias (sampled
  minus exhaustive) is **≤ 0.05**, not merely the absolute gap. Sign matters:
  R-P1.68's bias was +0.111.
- **P2 — the gap now resolves what it could not.** With 120 cases the
  standard error of a precision difference is small enough that a 0.111 bias
  would have been detected at ~3σ. Stated as a claim about the design; the
  receipt computes the realised standard error and reports whether the design
  could have detected R-P1.68's effect.
- **P3 — the realistic pools are measurable with a bounded bias.** At `n = 6` and
  `n = 8`, sampled precision differs from the `n = 4` cell in the direction
  R-P1.67 measured, and the `n = 8` cell completes within the declared budget.
  No claim that the sampled value equals the exhaustive one there — it cannot be
  computed.
- **P4 — the trend from R-P1.67 continues.** `n = 4 > n = 6 > n = 8` in
  precision at fixed `k` and `M`. R-P1.67 measured 0.444 / 0.139 / 0.111 at
  M=2000, 12 cases; the prediction is the ordering holds at 120 cases.
- **P5 — no leak.** The null arm (same spend, readings independent of truth) does
  not beat passive in more than a third of cases at any `n`.

Any prediction may fail and is kept. **P1 is again load-bearing**: if a
without-replacement sampler is still biased by more than 0.05 with 120 cases,
then sampling is the wrong instrument and the realistic pools stay unmeasured
until an exact non-enumerating posterior exists.

## What this card may and may not conclude

- It **may** say whether the bias R-P1.68 saw was duplicates or noise, and give
  the realistic pools' precision with a stated, bounded uncertainty.
- It **may not** claim the sampled numbers equal the exhaustive ones at `n = 6/8`
  — there is nothing to compare against, and the card says so per cell.
- It **may not** open E6. This is a measurement-method card; the headroom
  question is R-P1.60's and stays where it was.
- It **may not** retune R-P1.68. That card's failure stands.

## Controls and honesty

- The exhaustive `n = 3, 4` arms at **120 cases** use the identical code path
  (`M = None`), so a comparison is not across implementations.
- Two `M` values: if the gap shrinks when M grows, sampling error is the cause;
  if it does not, duplicates were.
- A mutation check: running the sampler **with** replacement at `M = 8000`, 120
  cases must reproduce R-P1.68's upward bias (within its recorded range). If it
  does not, the fixture changed and the run is `UNVERIFIABLE`.
- The receipt records the realised standard error per cell and the wall time per
  cell, so both P2 and the cost claim are checkable.
- Verdict vocabulary: `PASS` / `FAIL` / `UNVERIFIABLE`.

## Limits

One predicate, one cap rule, one sensor, one decoder. Uniform sampling over
distinct 3-edge completions; a pool where the cap rule rejects most candidates
would need rejection sampling and is not the case here. The 120-case set is drawn
from seeds disjoint from `DEV` but is still one generator — this is not an
independent corpus.

### The answer to R-P1.68's open question

R-P1.68 could not say whether its +0.111 was **duplicate weighting** or **sample
noise**. It was duplicates. Holding everything else fixed and drawing only
*distinct* completions moved the bias from +0.111 to **+0.019** on 120 cases
where the design resolves 0.111 at 5.5σ — so this is not the gap hiding in the
noise, it is the gap being removed.

The mutation arm corroborates it: the **old** sampler re-run at 120 cases still
shows **+0.047**, upward, on the same fixture. So the fixture did not move; the
sampler did.

### The failure is my budget, not the method

P3's threshold was `≤ 5 s/case`, written before I had timed `n = 8`. Measured:
`n = 6` 2.79 s, `n = 8` **10.23 s**. The cell is computable and its bias is
bounded by P1; the clause is a wrong guess about speed and is recorded FAILED
rather than retro-edited. The full grid took ~4.5 h.

### What this makes available

The realistic pools are now measurable **with a bounded bias**:

| n | pool | precision at k=8, M=2000 |
|---|---|---|
| 4 | 21.5 | 0.367 |
| 6 | 63 | 0.133 |
| 8 | 117 | 0.089 |

R-P1.67's trend continues and steepens. This is the first measurement of pools
63 and 117 in this lane, and it is the number any future probe-value claim

### Instrument note worth keeping

The first run sat at 0% CPU for 90 minutes with an empty log and looked hung. It
was working — the script printed only at the end, and 120 cases at `n = 8` is
~10 min per cell. Every cell now prints as it completes. A long run with no
progress output is indistinguishable from a stalled one, and I spent 90 minutes
treating a working job as dead.

### Limits

One predicate, one cap rule, one sensor, one decoder; uniform distinct sampling
over 3-edge completions. `n = 6/8` has **no exhaustive counterpart** — the
sampled value there carries P1's bound (+0.019 at n=4), not a measured
equivalence. `E6` stays closed.

### Where this leaves the arc

R-P1.60 → 69 is now a complete chain on one question: probe value under a
posterior. It ends with **no headroom for a learnt ranker**, a pool-size effect

any, should be about the operator's actual graphs rather than this fixture.

### Re-check: the data may still be there — diagnose read-only first

A second look changes the diagnosis in one important way. `lsblk` reports
**`FSTYPE=exfat` on `/dev/sdb` itself**, with no partition — the signature of a
**superfloppy** (filesystem at the start of the raw device, no partition table).
If that is what it has always been, the volume is **not necessarily damaged**:
`/mnt/sdb1` was a *mount point*.

What could not be done, and why the cause is still unidentified:

- `udisksctl mount -b /dev/sdb` — refuses: *"Not authorized to perform
  operation"* (polkit needs an agent and a password).
- `blkid` — **not installed** on air.
- `fsck.exfat` / `dump.exfat` — **not installed** (no `exfatprogs`).
- `dd if=/dev/sdb` — blocked by this session's guard, correctly: a raw device
  read is one character away from a raw write.

So the honest state is **unknown, not confirmed lost**. A superfloppy exfat is
recoverable and may be intact, so the first action for a human is *look*, not
re-create:

```
sudo mount -o ro /dev/sdb /mnt/sdb1 && ls /mnt/sdb1/fleet-sync/bundles | wc -l
```

Expect **175** if intact. Re-partitioning and re-seeding from the NAS apply only
if that fails — and re-seeding destroys whatever survives, which is why the
read-only look comes first.
