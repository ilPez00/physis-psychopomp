# Preregistration — R-P1.73: finite-radius crossing labels, and what a sliver costs

Claim `969e3ade-530c-4d53-9851-9cbe0e0a0c3c`, registered at **prior 0.5** before the run. Freeze on origin before
any measurement. Status at freeze: **not measured**.

D5's last unmeasured clause: *"finite-radius crossing labels and calibration."*
The mask half of D5 is answered — R-P1.70 found `BlindEstimate` is a rectangle by
construction, and R-P1.71 showed an event in a hole is identified like open space.
What has never been measured is what `visual_radius` does to the **labels** a
crossing emits, and whether the estimator's edge moves by exactly the radius.

## What the code does, verified before the card

`observable` reports a body hidden only when its **whole disc** is inside the
mask, and `_rect_bounds` reads the `pos` of `enter_occ` / `exit_occ` events. So
with `visual_radius = r`:

```
r=0.0  x=41 hidden   x=42 hidden      (point model: mask edge is 40)
r=1.0  x=41 hidden   x=42 hidden
r=2.0  x=41 visible  x=42 hidden      (eroded by 2: effective edge is 42)
```

measured on `o = (40, 60, 35, 65)` at `y = 50`. So the *effective* mask is eroded
by `r` on every side, and a crossing is reported where the **disc** fully enters,
not where the centre does. Two consequences are testable:

1. the inferred blind rectangle should shrink by exactly `r` per side;
2. a body that clips a corner emits **no** crossing at all, because its disc never
   fits inside — a sliver costs a label, not a small error.

## Design

R-P1.43's crossing corpus (two horizontal lanes, two vertical columns, the shape
that gives the estimator all four edges), at `r ∈ {0.0, 0.5, 1.0, 2.0}`, 5 seeds.

- **A — `r = 0`**: the point model. The anchor; its estimate is
  `(39.9, 60.1, 34.9, 65.0)` from R-P1.70.
- **B — `r > 0`**: same body paths, same mask, disc rule on.
- **C — corner clip**: a path that grazes a corner so that the disc is inside for
  no step at all, at `r = 0` and `r = 2`.

## Frozen predictions

- **P1 — the anchor reproduces.** At `r = 0` the estimate is the point-model
  rectangle (`39.9, 60.1, 34.9, 65.0` ± 0.05), matching R-P1.70.
- **P2 — the estimate shrinks by exactly the radius per side.** For each `r`, the
  four edges move inward by `r` within ±0.35: near edges increase, far edges
  decrease. Measured as four signed deltas, not as a verdict.
- **P3 — calibration is monotone, not affine.** The shrink tracks `r` across all
  three values (non-decreasing in `r` per edge), so a single `r` measurement
  cannot be extrapolated to another — the calibration clause the card's title
  names.
- **P4 — a sliver costs a label.** In the corner-clip arm at `r = 2`, the body
  emits **fewer** crossings than at `r = 0`, because its disc never fits inside.
  If the label count is unchanged, the disc rule is not reaching the emitter.
- **P5 — no oracle movement.** The oracle log is identical across `r`, since the
  radius is a sensor property, not a world one.

Any prediction may fail and is kept. **P2 failing would contradict the radius
documentation** and would be the more important finding.

- Each `r` changes one parameter and nothing else.
- The receipt records the estimate, the crossing count and the body paths, so P4

### The defect this card found, and fixed

The first run produced **`None` for every radius > 0**. Two functions that must
agree did not: `tr.visible[j]` uses the **disc** rule, `transition_rect`,
`_enter_side` and `_exit_side` used the **point** rule. With a radius, a
visibility change happens where the disc crosses, both endpoints of which are
*inside* the rectangle by the point test, so the labeller returned `None`,
`_enter_side` returned `corner`, and the emitter either labelled the crossing
`sweep` (which `_rect_bounds` ignores, so no estimate) or refused it outright
(`corner entry is not supported`).

Fixed by giving all three the radius: `transition_rect` tests coverage through a
new `_covered(cfg, rect, x, y)` helper, and `_enter_side` / `_exit_side` shift
their bounds inward by `r`. **262 existing tests still pass** with the change,
which is what makes it a fix rather than a swap.

The original mechanism, kept because it is the diagnosis:

With `visual_radius > 0` **every crossing label degrades to `side="sweep"`**, and
`_rect_bounds` counts only `left`/`right`/`bottom`/`top`, so the estimator gets
`samples = {left: 0, right: 0, bottom: 0, top: 0}` and returns `None`.

The cause is a predicate mismatch between two functions that must agree:

```python
tr.visible[j]               # uses the DISC rule (whole body must be inside)
transition_rect(...)        # uses inside_rect, the POINT rule
```

Traced on lane y=45 at `r = 1`: the body becomes hidden at step 121, x = 41.3.
`transition_rect` is called with x = 40.9 → 41.3, and **both are inside the
rectangle by the point rule** (the mask spans x ≥ 40), so it returns `None`, the
crossing is labelled `sweep`, and the edge evidence is discarded.

So `visual_radius` is honoured by the crossing *emitter* and silently ignored by
the crossing *labeller*. The two were written for different visibility models and
nothing compared them.

### Consequences, stated as limits rather than claims

- **No estimate can be produced for any `visual_radius > 0`** on a rectangular
  mask. The estimator's rectangle path is **radius-blind**, which is a stronger
  and more useful finding than P2's calibration claim would have been.
- P4 failed for the same reason: the corner-clip arm still emits two crossings at
  both radii, because the *emitter* compares visibility correctly — it is the
  *label* that loses the geometry. The sliver-cost question is therefore
  unanswered, not answered negatively.
- P5 failed because a `wall_bounce` time differs: with `r = 2` a body that grazes
  the corner stays "visible" a step longer, which moves the bounce. The oracle
  itself never changed — the check compared derived events, which the radius does
  legitimately affect. That was a bad check, not a leak.

### What closing D5 actually needs

A one-line alignment in `sim.py`: `transition_rect` must test the **same**
predicate the visibility pass uses, i.e. the disc rule when `visual_radius > 0`.
Until then, radius and the rectangle estimator cannot both be used, and this card
records that rather than a calibration curve.

`E6` stays closed.

## Prior art this card should have cited (correction, 2026-11-27)

**R-P1.44 (`partial-visibility-20261123`) already stated the geometry** this card's
P2/P3 confirm:

> "for radius r the blind region is the point-level one shrunk by r, and a
> centre-based predicate over-predicts blindness in a band of width r. The correct
> wording is: identifiable iff the whole body is outside the blind region."

So "the estimate shrinks by `r` per side" is a **confirmation** of R-P1.44, not a
discovery, and the card's title claim about *calibration* is milder than it reads.

What is genuinely new and additive, and is why the card still earned its run:

- **the defect.** R-P1.44 fixed the **law's wording**; it did not touch the
  **labeller**. `transition_rect`, `_enter_side` and `_exit_side` still compared
  points while `tr.visible` compared discs, so no estimate existed for any
  `visual_radius > 0`. That is a code defect in a different place from R-P1.44's
  finding, and it is fixed here with 262 tests unchanged.
- **the sliver as a count.** "A graze shallower than the radius emits no crossing"
  is R-P1.44's band, measured as a label count rather than as a verdict.

Two of my own fixtures were wrong first (a graze through the middle of the mask,
an oracle compared on visibility-derived timings) and are recorded above; that is
where most of this card's time went, not into the finding.
