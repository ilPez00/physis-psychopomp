## The store already had the lock; I was going to invent it

Read from `crates/physis-store/src/log.rs` at that revision:

- `append_observations_if(paths, items, condition)` — one cross-process lock
  around *load, condition, sequence assignment, append*. `condition(&existing)`
  runs **inside** it and `Ok(false)` aborts the whole batch.
- `observation_prefix` refuses a truncated tail:
  `"observation log has a torn tail; append refused without deleting evidence"`.
- `redact::scrub(&mut obs)` runs on every row immediately before the write.
- `Observation` carries `props: BTreeMap<String, String>` — typed facts beside
  the free-text body, which is a better home for our fields than JSON-in-body.
- Sequence exhaustion is checked (`checked_add`), not wrapped.

So the plan's "dedup under the store lock" was not a new mechanism: it is the
`_if` condition. What was missing is a *domain* key, and that is all this module
adds.

## What was implemented

`crates/physis-store/src/psychopomp.rs`, registered in `lib.rs`:

| rule | why |
|---|---|
| UTC `ingest_at` passed in by the caller; producer's `at` kept in `props["at_seconds"]` | reading simulated seconds as Unix time would date every row 1970 |
| only `evidence == "OBSERVED"` | a prediction is not a sighting |
| `provenance.source` starting `counterfactual:` refused | the producer never emits one; refusing beats relabelling |
| key `psychopomp:<subject>#<seq>` in `produced_by` | stable across runs, and visible to a reader |
| in-batch dedup before the store sees it; existing-log dedup by pre-filter; a **final condition inside the lock** aborts on a race | no duplicate row survives either path |
| `--dry-run` reads and validates, writes nothing | the caller decides when a world changes |
| torn tail refused | the store's own rule, not overridden here |

## CLI, smoke and concurrency (same session)

`feat/cli` at **`4f0ce96d8`** adds `physis import <schema> <file> [--path] [--dry-run]`.
It takes `--path` like `subject`, `object` and `claim`, not a positional — the
first smoke run failed with `unexpected argument '--path' found` because it did,
and the command was changed rather than the habit.

Smoke on a fresh world, using Psychopomp's own
`research/fixtures/observation-v1.sample.jsonl`:

| step | measured |
|---|---|
| dry run | `rows_appended = 0`, **no log file created** |
| first import | `5` appended |
| re-import | `0` appended, `5` recognised as duplicates |
| readback | `physis subject --path … 'episode:0:0'` returns **5 rows** |
| torn tail | exit 1, `observation log has a torn tail; refusing to append over it` |

That is the round trip the integration contract asked for, at CLI level: export →
import → query, with the store's own reader.

**Concurrency, measured rather than argued.** Two `physis import` processes over
the same export into the same world:

```
exit codes: 1 0
rows in log: 5      unique produced_by: 5
stderr:               Error: observation log changed while importing; re-run to recompute duplicates
```

One process appended all five; the other **aborted** on the in-lock condition
instead of duplicating, and the log holds five rows with five distinct keys. The
abort is the designed behaviour: a race is reported, never silently resolved.

## Round trip with real simulator rows (same session)

Producer side, on pansa: `scripts/e1-roundtrip-export.py` runs the 24 R-P1.48
cells as **24 separate episodes** and exports them through
`psychopomp.export.observation_records`.

Why separate episodes: a record's identity is `(subject, seq)` and
`subject = episode:<seed>:<episode>`. Reusing `episode:0` for all 24 would give one
subject, so the importer's dedup would keep the first and skip twenty-three —
correct behaviour, worthless evidence.

```
episodes=24 rows=24 subjects=24
```

Consumer side, on omo, with the branch binary:

```
import  exit-cells.jsonl   → rows_read 24, rows_appended 24
import  again              → rows_read 24, rows_appended 0, rows_skipped_duplicate 24
physis subject 'episode:0:0'
  rows: 1  subject: episode:0:0  source: psychopomp
  at: 2026-11-23T08:33:08        (UTC ingest time, explicit)
  props.at_seconds: 2.1          (simulated seconds, preserved separately)
  props.psychopomp_kind: exit_occ
```

**One wrinkle, recorded rather than smoothed:** the stored row *does* carry
`produced_by: psychopomp:episode:0:0#0` — checked in the raw log line — but
`physis subject --json` does not render that field. So dedup is proven by the
re-import (`24` skipped), not by the readback. A consumer that needs the key must
read the log line or ask for it; a reader that trusts `subject` output would think
the row has no producer.

## Linking the two stores

The evidence is now queryable from the hypothesis side, not only from a receipt:

```
physis-core hypothesis explain 26f1ebc3-93c6-453a-940f-85c1428fd36b
  STATUS: supported (Confidence: 0.90)
  ✓ [cli] Producer export … sha256 7badfc82…, 24 rows over 24 distinct episodes.
          Import into … rows_appended 24; re-import 0 appended, 24 duplicates.
          … Audit packet sha256 91f3236b…, packet-verify VERIFIED over 24 rows.
          Caveat: physis subject does not render produced_by …
```

**The binding is two hashes, not a copied number.** The producer-side file
(`7badfc82…`) and the consumer-side audit packet (`91f3236b…`, verified over the
24 stored rows) are both cited, so someone re-reading the claim can re-derive each
independently: the first from Psychopomp's export, the second from the store. A
row count alone would have been a claim about two files nobody could check.

Caveat carried into the evidence text itself: dedup is proven by the re-import
counts, because `physis subject` does not render `produced_by`.

## The partly-known batch was broken, and the error said "try again"

Measured on the branch (`feat/psychopomp-import`), import 5 rows, then import a
batch of 6 in which those 5 are already present:

```
before the fix:  Error: observation log changed while importing; re-run to recompute duplicates
after  the fix:  {"rows_appended":1,"rows_skipped_duplicate":5}
```

The in-lock predicate judged **every key the caller had read**, not the rows
being appended, so any overlap with the existing log refused the whole batch.
Worse than the failure was its message: it named a race, and a retry could never
converge because the overlap is permanent. The concurrency receipt above shows
the same string for a genuine race — so the two were indistinguishable in the
one place an operator would look.

Fixed at `65e3e02f2`: the predicate now sees only the pending keys, while the
read / appended / skipped counts stay separate. The concurrency guarantee is
unchanged: a concurrent writer that claims one of *these* keys still aborts.
The case is pinned twice — a unit test (`a_partly_known_batch_appends_only_the_new_rows`)
and a step in the committed smoke (`2773ccbbc`), because the shell transcript it
was first measured in is not a regression test.

Also corrected: the store module had been committed unformatted, so
`cargo fmt --check` would have failed on the branch for reasons unrelated to any
of this. It is formatted now; that check had never been run here before.
